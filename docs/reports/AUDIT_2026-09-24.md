## 3. Hard-coded behaviour, reviewed

- **Timing and phrases:** all in `config/keel.toml`, each value with its
  source. Nothing timing-related is hard-coded in the kernel.
- **Scenario knowledge:** none. The mock environment, scripted interpreter
  and probe are data-driven, and the showcase keeps its data in
  `eval/showcase.py`, outside `keel/`.
- **`config/keel.toml` sits outside the package.** `load_config()` reads
  it relative to the repo. This works from a checkout, which is how the kit
  is expected to run us. It is noted rather than changed, because moving the
  file would break the "every value is commented at its source" layout.
  Revisit if the kit installs a wheel.

## 4. Is it worth it? An honest assessment against the guide's scoring

**Strong where it counts after perception.** Interruption Recovery (35%)
and Safety & Protocol (10%) are what the kernel is built for:
- Cancellation is dependency-precise and happens in the same ms (I2).
- There are 0 double bookings over 3,072 fault and timing combinations.
- No success is ever claimed without a success result.
- Every action is validated against the schema before it leaves Keel.

The prior-art check still holds. Pipecat cancels on *any* interruption by
default (`cancel_on_interruption=True`), and LiveKit cancels nothing by
default and tells developers to guard mutating tools by hand. Deriving the
policy from the manifest and cancelling only calls whose inputs changed is
a real, defensible difference.

**The decisive gap is the slow path.** Nothing yet turns text, audio or
frames into an `Interpretation`. Against the real kit today, Keel would
compile the manifest, say "One moment." and wait: Task Completion (40%) and
most of the multimodal ×1.5 would score near zero. Every kernel guarantee
is conditional on phase 4. The next unit of effort should go to the
interpreter (LLM-to-Goal with the existing schema, ASR, frame reading), not
to more kernel polish.

**Known weak spots, measured:**
- **A cancelled in-flight write that never answers blocks its tool until
  the Keel timeout.** In `test_in_flight_write_invalidated_is_probed_before_the_new_write`,
  the correction lands at 1,500 ms and the corrected booking goes out at
  11,300 ms. The first spoken response is still immediate. Shortening this
  safely needs the kit's cancel semantics (K18/K19): probing early could read
  "not found" while the old write is still running.
- **Read recall on unseen tools is 0.41 at the shipped threshold.** This
  costs latency only (uncertain tools wait behind the fence), never
  correctness.
- **The 600 ms fence and 0.6 clarify threshold are still taken from the
  literature**, not measured by us (phase 4).

## 5. Trace console (new)

`keel/console/`, a single self-contained HTML page. It is light theme only,
because it will be read on projectors and in screenshots. It needs no
libraries and works offline (IBM Plex loads from Google Fonts when
available, with system fallbacks).

```
python -m eval.showcase                            # traces/*.jsonl + traces/console.html
python -m keel.console traces/*.jsonl -o out.html  # any traces
```

What each session shows, in the order a reviewer asks:
1. **Safety invariants I1-I5**, checked from the trace itself. I4 needs the
   mock world, and says "unchecked" when rendered from a file alone rather
   than claiming a pass.
2. **Time to first response** per user turn: the slowest and the median.
3. **Timeline** in virtual ms. Read-only calls are teal and writes violet;
   fence holds are hatched, a cancel is a red ✕ with its reason
   (`destination v1->v2`), and an in-doubt outcome is a dashed amber line.
   Hovering shows the full call history.
4. **Conversation**: user turns, with end-of-turn marked, interleaved with
   what Keel said, each tagged with its latency.
5. **Final state**: the final text and every slot's version history
   (`v1 Koramangala → v2 Indiranagar`, corrected by the user). Low-confidence
   perceptions that were held back and proposals refused by a lock are shown
   too.
6. **Tool calls**, expandable: status history, slot versions read, and the
   compiler's evidence for the call's safety class.
7. **Event log**: filter by direction, search, and click to see the raw
   record.

The five showcase sessions follow the guide's use cases: a self-repair
before sending, an in-car reroute, "did it go through?", a write that lands
anyway, and an unclear camera frame followed by a clarification. They are
synthetic: the kernel, compiler and probe are real, but the interpretations
are scripted. The console marks them as such. CI runs `python -m
eval.showcase`, which fails on any invariant violation.
