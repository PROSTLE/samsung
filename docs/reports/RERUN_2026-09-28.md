## What we found in the first run

- **9 of the 16 silent scenarios were our machine, not the model.** From `agent.log`
  and each scenario's `stream_start_time`: in finance_12, 14, 15, 16, 19, 20, 21 and 22
  the agent received its job 28-64 s after FDB-v3 started streaming, after the caller had
  finished, and housing_04's room never got an agent. Between 09:20 and 09:22 UTC the log
  shows DNS failures, failed recording uploads being retried, and the worker reconnecting
  to LiveKit. The earlier report said "in 12, Gemini Live never produced a user turn";
  that was wrong for these nine.
- **Many argument failures were the model changing what the user said**: spelled IDs
  written with dashes the user never said (the same scenario gave "P52" in one recording
  and "P-5-2" in the other), singular for plural search terms, words dropped from places.
- **Some failures cannot be fixed without fitting the answer key.** The tool schema
  documents dates as '2026-08-20' while the expected value is "October 7";
  `update_search_filter.value` is declared a string while 1800 is expected;
  `pets_allowed` is expected on `search_apartments`, whose template signature has no such
  parameter. We left these alone; FDB-v3's judge compares by meaning.

## What changed

1. `livekit.record = false` (`keel/config.py`, used by both agents): no session
   recording uploads to LiveKit Cloud. Replays use FDB-v3's own audio.
2. `AgentServer(load_threshold=0.95)` (`keel/livekit/agent.py`): LiveKit stops giving a
   worker jobs above a machine-wide CPU load of 0.7 by default, and FDB-v3 runs its speech
   recognition on the same machine between scenarios.
3. Three general sentences in `config/fdb_v3.toml` `extra_instructions`: join a code or ID
   spelled one character at a time; keep search terms, names and places in the user's own
   words; do every step of a multi-step request. No benchmark item, value or format is
   named.
4. `eval/form_equivalence.py` (+ `tests/test_form_equivalence.py`) makes the
   "compared by meaning" estimate reproducible; it gives 63/100 on the first run, the
   figure the earlier report stated.

In the second run no agent joined a room after the caller had finished (the slowest was
ready 6.5 s after the stream started).

## Third run (21:13 UTC): acting on what the user said

The 16:08 run's failures included 8 scenarios where the model asked a follow-up question
instead of calling a tool (for example asking for street addresses after the user
described both places), and values written in a different style from the tool's own
examples. Two general sentences were added to `extra_instructions` (act on values the
user already gave; follow the style of the tool's example values), and one was sharpened
(keep small words such as "the" or "my"). A smoke run of housing_17 showed the change:
the agent now calls `calculate_commute` with the corrected mode instead of asking.

A first attempt at the full run (19:36 UTC) is invalid: the machine lost its network

meaning.

## Still open

- First response is still slower than the paper's Gemini Live 3.1 (mean 4.96 s against
  3.95 s). Keel's own hold is about 0.6 s of it. A spoken acknowledgement while a call is
  held is not yet made on the realtime pipelines, which have no separate text-to-speech.
- 5 scenarios got no response and 13 answered without the expected tool call.
- One run per configuration; Gemini Live is not deterministic, so part of the difference
  between the runs is run-to-run variation.
